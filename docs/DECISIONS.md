# Decisions

Record every choice that is not fixed by `docs/SPEC.md`, and every deviation from it. Newest at the bottom.
Format: `date | decision | why | impact on experiments`.

2026-11-23 | Pages are file-backed (`pread`/`pwrite`), 4096 bytes, fixed-width int32 tuples with padding | Query time is the main metric; page I/O counted exactly at the DiskManager | Wall-clock time includes OS page cache effects; document in the report's setup text
2026-11-23 | Every join except the last materializes its output to a temp heap file | One join active at a time gets the full buffer budget B; formulas use exact M, N | Intermediate-result I/O is counted and included in the estimator
2026-11-23 | Final output goes to a Sink that counts rows and checksums; no page writes for the final result | The join formulas exclude output cost | Output cardinality reported separately
2026-11-23 | Oracle is SQLite via Python stdlib on CSVs exported by the generator | Required by the proposal | Result comparison is by row count plus an order-insensitive checksum
2026-11-23 | `BufferPool::NewPage` always marks the frame dirty, regardless of the dirty flag later passed to `Unpin` | A freshly allocated page has never been written to disk, so it must be flushed eventually or its contents (and anything the caller writes into it) are lost; `Unpin`'s dirty flag is sticky (OR-only) and cannot clear it | Eviction/flush write counts include one write per page ever allocated via `NewPage`, even if the caller's own writes were later undone; unit tests assert on this |
2026-11-23 | `BufferPool::Reset()` calls `FlushAll()` before emptying the pool (not just a bare clear) | Silently dropping dirty frames would lose data and make repeated "cold start" runs non-reproducible; SPEC.md only says Reset "empties the pool" but flushing first is the only safe reading | `Reset()` can itself produce page writes, which is included in `page_writes` right before a measured run begins — callers should snapshot counters after Reset, not assume Reset is a no-op on stats |
2026-11-23 | `Sailors.sid` and `Boats.bid` are dense, unique ids `0..count-1` assigned at generation time; `Reserves` samples these ids directly (no separate lookup table) | SPEC.md already calls both unique; dense ids make FK sampling, Zipf-over-ranks, and join-correctness checking trivial without changing any query semantics | Reserves.sid/bid are always valid foreign keys by construction; zipf skew is defined over the rank order `0..count-1` |
2026-11-23 | No catalog file in `data/`; every tool recomputes `TableStats` with one scan of each heap file at startup (`Catalog::ComputeTableStats`) | The repo layout in SPEC.md section 2 lists no catalog file, and recomputing is cheap at this project's scale; avoids inventing a serialization format before Phase 3 (`run_query`) shows what it actually needs | Any tool that opens a table must call `ComputeTableStats` once before reading its stats |
2026-11-23 | Generator correlation (`--corr`) blends an independent uniform draw with a value derived from the correlated column's rank, via `round(indep*(1-c) + corr*c)` clamped to the valid range | SPEC.md section 5 requires `Sailors.rating`~`Sailors.age` and optionally `Boats.color`~`Boats.bid` correlation but does not fix a formula | `corr=0` reproduces independent columns exactly (verified in `test_data_generator`); `corr=1` makes rating/color a deterministic function of age/bid |
2026-11-23 | `--key-dist zipf` applies the same Zipf skew to both `Reserves.sid` and `Reserves.bid` | SPEC.md marks `R.bid` skew as optional; applying it uniformly with one `--zipf-theta` flag is the simplest reading and matches the E4 experiment's intent (skew hurts hash joins) | A single `--zipf-theta` controls skew on both join keys; there is no independent toggle for sid-only skew |
2026-11-23 | **Bug fix:** `DiskManager::OpenFile` now sets `page_count` from the real on-disk file size (`lseek`), not 0 | `gen_data` happened to produce complete files only by accident: the catalog's full-table scan right after generation cascaded an LRU eviction that flushed the still-dirty tail pages as a side effect. Any tool that reopens a file in a *new* `DiskManager` (e.g. `run_query` after `gen_data` exits) would otherwise see `page_count=0` and silently read zero rows. Found by `test_bnlj`'s I/O-formula check, which reopens heap files in a fresh `DiskManager`/`BufferPool` | All page-count queries on a reopened file are now correct; `gen_data` also now calls `BufferPool::FlushAll()` explicitly before exit instead of relying on that incidental cascade |
2026-11-23 | Order-insensitive result checksum: per tuple, fold columns into a 64-bit FNV-1a hash (offset `0xcbf29ce484222325`, prime `0x100000001b3`, `h ^= col; h *= prime` per column), then sum the per-tuple hashes mod 2^64 | SPEC.md section 9 requires "row count plus an order-insensitive checksum" but doesn't fix an algorithm; summing avoids order sensitivity, a strong per-row hash avoids accidental cancellation/collision | Implemented once in `src/exec/checksum.h` and mirrored by hand in `scripts/oracle_check.py`; any change to one must be mirrored in the other or `oracle_check.py` will report false mismatches |
2026-11-23 | `BNLJ` decodes each block's outer tuples into a private `vector<Tuple>` sized to the block (`buffer_pages - 2` pages' worth) and pins only one page at a time in the `BufferPool`, rather than literally holding `buffer_pages - 2` frames pinned simultaneously | Every page access still goes through the buffer pool and is counted identically to the textbook pinned-block version (verified in `test_bnlj`'s formula check); holding real pins for the whole block isn't needed to get correct I/O counts and would complicate the implementation for no measurable benefit | `BufferFullError` can't be triggered by BNLJ's own outer-block reading (it never holds more than 1 pin); this only matters if a future phase needs to simulate pin contention, which no current experiment does |
2026-11-23 | `run_query` (Phase 3) hardcodes the QA plan: BNLJ with Sailors as the fixed outer table, Reserves as inner, predicates always pushed into the join scan | There is no plan builder yet (that's Phase 7/8's `plan_builder`/pushdown toggle); QA's "two orders for which table is outer" (SPEC.md section 8) and a pushdown on/off switch are deferred until the plan builder exists | `run_query`'s CLI flags only cover QA's constants (`--rmin`, `--dmin`) and `--buffer-pages`, not join order or pushdown |
2026-11-23 | **Bug fix:** temp files created by `ExternalSort`/`GHJ` (`NewTempHeap`) now `std::filesystem::remove(path)` before `DiskManager::OpenFile`, instead of relying on `O_CREAT` | Combined with the Phase 3 `OpenFile`-reads-real-size fix, reusing the same `temp_path_prefix` across two separate `ExternalSort`/`SMJ`/`GHJ` invocations (e.g. the same query run twice with a fixed prefix) made the second run see the first run's leftover pages as already allocated and append past them instead of starting fresh, silently corrupting the sort/partition. Found via `test_smj`/`test_ghj`, which reuse one `TempPath(...)` prefix across a buffer-size sweep | Every `ExternalSort`/`GHJ` temp file is now guaranteed to start empty regardless of what ran before at that path |
2026-11-23 | `ExternalSort::PrepareSortedRuns` calls `BufferPool::FlushAll()` immediately after run formation, even when zero merge passes follow | Without it, run formation's output pages could stay resident and dirty indefinitely if nothing else evicted them, so a later reader (the fused merge, or a reopening process) could get a free cache hit instead of the "P writes" the cost model (3(M+N)) attributes to this phase — fine for correctness, but made the I/O-formula unit tests nondeterministic depending on incidental pool pressure | Matches the same fix already applied to `gen_data` (Phase 2) and the eviction logic already in `BufferPool`; makes formation's write cost deterministic regardless of what else shares the pool |
2026-11-23 | **Finding, not a bug:** `GHJ`'s measured I/O can be several times `3(M+N)` when `buffer_pages` gives the physical pool little to no slack beyond `num_partitions + 1` frames (e.g. `buffer_pages` itself as the only headroom) | With `buffer_pages - 1` partitions all being appended to in hash-random (not round-robin) order, a partition's only-partially-filled output page becomes the LRU victim before it's touched again whenever the pool is near its minimum, forcing a write-then-reread cycle per revisit instead of one write at the end. Reproduced at base scale: `buffer_pages=60` (pool size 60, 59 partitions) measured ~2.9x the formula; giving the same logical `buffer_pages` a much larger *physical* pool (not changing the partition count) brought it to ~0.8x the formula | For E3/E6-style experiments, report GHJ numbers with enough physical buffer headroom to avoid this thrashing artifact, or note it explicitly as a finding under "how much do indexes and buffer size matter" — it is a real property of hash partitioning with randomly-routed keys, not an implementation defect (confirmed via `test_ghj`'s correctness checks, which always match the reference executor regardless) |
2026-11-23 | `run_query` now takes `--method bnlj\|smj\|ghj` (all three run the same hardcoded QA plan: S outer, R inner, predicates pushed down) | A self-review against `PLAN.md`/`SPEC.md` found that Phase 4's "QA via SMJ and GHJ match SQLite" acceptance criterion had only ever been checked with an uncommitted scratch binary, not reproducibly from the repo. `oracle_check.py` gained a matching `--method` flag | Re-ran `oracle_check.py` for all three methods at base scale (scale=1.0, 494+2500 pages) and confirmed all three match the SQLite oracle exactly; this is still ahead of the real plan builder (Phase 7), so join method here is a manual CLI choice, not a cost-based decision |
