# Decisions

Record every choice that is not fixed by `docs/SPEC.md`, and every deviation from it. Newest at the bottom.
Format: `date | decision | why | impact on experiments`.

2026-11-23 | Pages are file-backed (`pread`/`pwrite`), 4096 bytes, fixed-width int32 tuples with padding | Query time is the main metric; page I/O counted exactly at the DiskManager | Wall-clock time includes OS page cache effects; document in the report's setup text
2026-11-23 | Every join except the last materializes its output to a temp heap file | One join active at a time gets the full buffer budget B; formulas use exact M, N | Intermediate-result I/O is counted and included in the estimator
2026-11-23 | Final output goes to a Sink that counts rows and checksums; no page writes for the final result | The join formulas exclude output cost | Output cardinality reported separately
2026-11-23 | Oracle is SQLite via Python stdlib on CSVs exported by the generator | Required by the proposal | Result comparison is by row count plus an order-insensitive checksum
2026-11-23 | `BufferPool::NewPage` always marks the frame dirty, regardless of the dirty flag later passed to `Unpin` | A freshly allocated page has never been written to disk, so it must be flushed eventually or its contents (and anything the caller writes into it) are lost; `Unpin`'s dirty flag is sticky (OR-only) and cannot clear it | Eviction/flush write counts include one write per page ever allocated via `NewPage`, even if the caller's own writes were later undone; unit tests assert on this |
2026-11-23 | `BufferPool::Reset()` calls `FlushAll()` before emptying the pool (not just a bare clear) | Silently dropping dirty frames would lose data and make repeated "cold start" runs non-reproducible; SPEC.md only says Reset "empties the pool" but flushing first is the only safe reading | `Reset()` can itself produce page writes, which is included in `page_writes` right before a measured run begins — callers should snapshot counters after Reset, not assume Reset is a no-op on stats |
2026-11-23 | `Sailors.sid` and `Boats.bid` are dense, unique ids `0..count-1` assigned at generation time; `Reserves` samples these ids directly (no separate lookup table) | SPEC.md already calls both unique; dense ids make FK sampling, Zipf-over-ranks, and join-correctness checking trivial without changing any query semantics | Reserves.sid/bid are always valid foreign keys by construction; zipf skew is defined over the rank order `0..count-1` |
2026-11-23 | No catalog file in `data/`; every tool recomputes `TableStats` with one scan of each heap file at startup (`Catalog::ComputeTableStats`) | The repo layout in SPEC.md section 2 lists no catalog file, and recomputing is cheap at this project's scale; avoids inventing a serialization format before Phase 3 (`run_query`) shows what it actually needs | Any tool that opens a table must call `ComputeTableStats` once before reading its stats |
2026-11-23 | Generator correlation (`--corr`) blends an independent uniform draw with a value derived from the correlated column's rank, via `round(indep*(1-c) + corr*c)` clamped to the valid range | SPEC.md section 5 requires `Sailors.rating`~`Sailors.age` and optionally `Boats.color`~`Boats.bid` correlation but does not fix a formula | `corr=0` reproduces independent columns exactly (verified in `test_data_generator`); `corr=1` makes rating/color a deterministic function of age/bid |
2026-11-23 | `--key-dist zipf` applies the same Zipf skew to both `Reserves.sid` and `Reserves.bid` | SPEC.md marks `R.bid` skew as optional; applying it uniformly with one `--zipf-theta` flag is the simplest reading and matches the E4 experiment's intent (skew hurts hash joins) | A single `--zipf-theta` controls skew on both join keys; there is no independent toggle for sid-only skew |
2026-11-23 | **Bug fix:** `DiskManager::OpenFile` now sets `page_count` from the real on-disk file size (`lseek`), not 0 | `gen_data` happened to produce complete files only by accident: the catalog's full-table scan right after generation cascaded an LRU eviction that flushed the still-dirty tail pages as a side effect. Any tool that reopens a file in a *new* `DiskManager` (e.g. `run_query` after `gen_data` exits) would otherwise see `page_count=0` and silently read zero rows. Found by `test_bnlj`'s I/O-formula check, which reopens heap files in a fresh `DiskManager`/`BufferPool` | All page-count queries on a reopened file are now correct; `gen_data` also now calls `BufferPool::FlushAll()` explicitly before exit instead of relying on that incidental cascade |
2026-11-23 | Order-insensitive result checksum: per tuple, fold columns into a 64-bit FNV-1a hash (offset `0xcbf29ce484222325`, prime `0x100000001b3`, `h ^= col; h *= prime` per column), then sum the per-tuple hashes mod 2^64 | SPEC.md section 9 requires "row count plus an order-insensitive checksum" but doesn't fix an algorithm; summing avoids order sensitivity, a strong per-row hash avoids accidental cancellation/collision | Implemented once in `src/exec/checksum.h` and mirrored by hand in `scripts/oracle_check.py`; any change to one must be mirrored in the other or `oracle_check.py` will report false mismatches |
2026-11-23 | `BNLJ` decodes each block's outer tuples into a private `vector<Tuple>` sized to the block (`buffer_pages - 2` pages' worth) and pins only one page at a time in the `BufferPool`, rather than literally holding `buffer_pages - 2` frames pinned simultaneously | Every page access still goes through the buffer pool and is counted identically to the textbook pinned-block version (verified in `test_bnlj`'s formula check); holding real pins for the whole block isn't needed to get correct I/O counts and would complicate the implementation for no measurable benefit | `BufferFullError` can't be triggered by BNLJ's own outer-block reading (it never holds more than 1 pin); this only matters if a future phase needs to simulate pin contention, which no current experiment does |
2026-11-23 | `run_query` (Phase 3) hardcodes the QA plan: BNLJ with Sailors as the fixed outer table, Reserves as inner, predicates always pushed into the join scan | There is no plan builder yet (that's Phase 7/8's `plan_builder`/pushdown toggle); QA's "two orders for which table is outer" (SPEC.md section 8) and a pushdown on/off switch are deferred until the plan builder exists | `run_query`'s CLI flags only cover QA's constants (`--rmin`, `--dmin`) and `--buffer-pages`, not join order or pushdown |
2026-11-23 | **Bug fix:** temp files created by `ExternalSort`/`GHJ` (`NewTempHeap`) now `std::filesystem::remove(path)` before `DiskManager::OpenFile`, instead of relying on `O_CREAT` | Combined with the Phase 3 `OpenFile`-reads-real-size fix, reusing the same `temp_path_prefix` across two separate `ExternalSort`/`SMJ`/`GHJ` invocations (e.g. the same query run twice with a fixed prefix) made the second run see the first run's leftover pages as already allocated and append past them instead of starting fresh, silently corrupting the sort/partition. Found via `test_smj`/`test_ghj`, which reuse one `TempPath(...)` prefix across a buffer-size sweep | Every `ExternalSort`/`GHJ` temp file is now guaranteed to start empty regardless of what ran before at that path |
2026-11-23 | `ExternalSort::PrepareSortedRuns` calls `BufferPool::FlushAll()` immediately after run formation, even when zero merge passes follow | Without it, run formation's output pages could stay resident and dirty indefinitely if nothing else evicted them, so a later reader (the fused merge, or a reopening process) could get a free cache hit instead of the "P writes" the cost model (3(M+N)) attributes to this phase — fine for correctness, but made the I/O-formula unit tests nondeterministic depending on incidental pool pressure | Matches the same fix already applied to `gen_data` (Phase 2) and the eviction logic already in `BufferPool`; makes formation's write cost deterministic regardless of what else shares the pool |
2026-11-23 | **Finding, not a bug:** `GHJ`'s measured I/O can be several times `3(M+N)` when `buffer_pages` gives the physical pool little to no slack beyond `num_partitions + 1` frames (e.g. `buffer_pages` itself as the only headroom) | With `buffer_pages - 1` partitions all being appended to in hash-random (not round-robin) order, a partition's only-partially-filled output page becomes the LRU victim before it's touched again whenever the pool is near its minimum, forcing a write-then-reread cycle per revisit instead of one write at the end. Reproduced at base scale: `buffer_pages=60` (pool size 60, 59 partitions) measured ~2.9x the formula; giving the same logical `buffer_pages` a much larger *physical* pool (not changing the partition count) brought it to ~0.8x the formula | For E3/E6-style experiments, report GHJ numbers with enough physical buffer headroom to avoid this thrashing artifact, or note it explicitly as a finding under "how much do indexes and buffer size matter" — it is a real property of hash partitioning with randomly-routed keys, not an implementation defect (confirmed via `test_ghj`'s correctness checks, which always match the reference executor regardless) |
2026-11-23 | `run_query` now takes `--method bnlj\|smj\|ghj` (all three run the same hardcoded QA plan: S outer, R inner, predicates pushed down) | A self-review against `PLAN.md`/`SPEC.md` found that Phase 4's "QA via SMJ and GHJ match SQLite" acceptance criterion had only ever been checked with an uncommitted scratch binary, not reproducibly from the repo. `oracle_check.py` gained a matching `--method` flag | Re-ran `oracle_check.py` for all three methods at base scale (scale=1.0, 494+2500 pages) and confirmed all three match the SQLite oracle exactly; this is still ahead of the real plan builder (Phase 7), so join method here is a manual CLI choice, not a cost-based decision |
2026-11-23 | The paged B+ tree stores one key-to-Rid entry per leaf slot (not a bucket/overflow-page scheme for duplicates); a leaf split is positioned to never cut through a run of equal keys, so an internal separator is always a valid upper bound | SPEC.md requires "insert, range, duplicates" but doesn't fix a duplicate-handling scheme; keeping one flat sorted array per leaf (like the data layout already used for heap pages) is the simplest correct option | If a single key's duplicate count alone exceeds one leaf's capacity (~340 entries at the default page/tuple size), the split-boundary adjustment falls back to splitting mid-run anyway — a known, documented, untested edge case that doesn't arise for any key actually indexed in this project (Sailors.sid is unique) |
2026-11-23 | **INLJ's "outer" is Reserves (R), not Sailors (S)**, unlike BNLJ/SMJ/GHJ which all use S as the outer/left side | INLJ structurally requires the side *without* an index to drive the probe and the side *with* the index to be probed; the index is built on `Sailors.sid` (SPEC's own proposal text: "for every tuple of R, probe an index on S"), so R must be outer. `INLJ`'s output schema is therefore (R columns, S columns) — the reverse column order from the other three joins | `run_query --method inlj` prints "R outer, S inner (indexed)" to make this visible; `Projection` resolves columns by name, so this doesn't affect QA's final projected output |
2026-11-23 | Index build (`BPlusTree` bulk-inserted via a full heap scan) happens once, before `bp.Reset()`/the measured-I/O snapshot in `run_query` | SPEC.md section 12 describes "build indices and statistics" as a step before "run all plans" in the one-command pipeline — building the index is setup, not part of the join's own measured cost | `--method inlj`'s reported Reads/Writes reflect only the probe phase (`M` outer-scan pages + `\|R\|` index probes), not the one-time index construction cost |
2026-11-23 | `scripts/run_experiments.py` writes the full SPEC.md section 10 CSV schema now, with `est_io`/`est_out_rows` left blank | Those two columns need the cost estimator, which doesn't exist until Phase 8; filling in every other column now (reads_base/reads_index/reads_temp/writes_temp/buffer_hits/ghj_overflow_partitions all come straight from `run_query`'s per-kind counters) avoids changing the CSV schema again later | `run_query` gained matching `ReadsBase:`/`ReadsIndex:`/`ReadsTemp:`/`WritesTemp:`/`BufferHits:`/`GhjOverflowPartitions:` output lines so the Python runner can parse them |
2026-11-23 | `configs/qa_methods.json` uses `scale=0.1` (not the full base scale of 1.0) for the Phase 6 showcase table and buffer-size sweep | "Real measured numbers," per PLAN.md's Phase 6 wording, not necessarily full base scale; 0.1 keeps the whole experiment (4 methods + a 5-point sweep) under a few seconds while still being substantive (S~50 pages, R~125 pages, 3591 output rows) | The technical report's final numbers (Phase 9, `configs/e1..e6.json`) are a separate, later decision — this config is for the presentation-slice showcase only |
2026-11-23 | QB's two left-deep join orders (order1/order2) always put Reserves (R) as the outer/accumulated-left side of both joins, and whichever of Sailors or Boats is the inner as a plain (optionally filtered) base table scan on the right | This is required for INLJ to be usable at either join step in either order: the only indices this project builds are on `S.sid` and `B.bid`, and `ResolveIndexInput` (plan_builder.cpp) only recognizes a plain scan or a selection directly over one as a valid INLJ inner | `src/plan/qb_plan.h`'s `BuildQBPlan` is the single source of truth for this shape; a hypothetically different QB tree shape (e.g. S or B as the accumulated left side) is not supported by the current `PlanBuilder` |
2026-11-23 | INLJ's inner-side predicates (SPEC.md pushdown) are always applied as a post-filter immediately after that specific join step, never truly "pushed into" the index probe | The index is keyed on sid/bid, not on the filter columns (rating, age, color), so there is no way to push rating/age/color filtering into an equality lookup on a different column; applying it right after the join is the closest available approximation to "pushdown" for an INLJ inner | `PlanBuilder::ResolveIndexInput` extracts a `kSelection` wrapping the inner scan and re-applies it as a `Selection` over the join's combined output instead of filtering before the probe |
2026-11-23 | **Bug fix:** `run_query --method inlj` (QA) and `--method1/--method2 inlj` (QB) now skip rebuilding the index if it isn't empty | The index file persists across separate `run_query` invocations on the same `--data-dir` (intentional: build once, reuse across many plan runs — SPEC.md section 12). The code previously re-inserted every row unconditionally on every invocation, so a second INLJ-using call duplicated every index entry on top of the first, a third tripled it, etc. Found via `scripts/check_qb_plans.py`, which calls `run_query` 64 times against the same data directory — 27 of the 64 plans (every one touching INLJ) returned inflated row counts that grew with how many prior INLJ invocations had run | Both `RunQA` and `RunQB` in `run_query.cpp` now check `index.Empty()` before scanning the table to build it |
2026-11-23 | **Bug fix:** in `RunQB`, `bp.Reset()` (the cold-start snapshot) moved to before `PlanBuilder::Build()` instead of after | `PlanBuilder::Build()` eagerly executes and materializes every non-outermost join as part of constructing the tree, so a 2-join QB plan's first join (and its temp-file write) was running entirely before the "before" snapshot was taken, excluding its I/O and time from everything reported. Found by noticing a BNLJ-based first join reported implausibly low `ReadsBase` (1, not the few hundred the formula predicts) | Both the I/O counters and the wall-clock timer now wrap `Build()` + `Sink::Run()` together, not just the latter |
2026-11-23 | `GroupBy` only implements the in-memory hash-aggregate path, not the sort-based alternative SPEC.md mentions | SPEC.md section 6 explicitly calls out QC as the small-group-count case (`S.rating`: 10 distinct values) suited to a hash aggregate; no query in this project's set needs the sort-based path (which would matter for a large group count, or for delivering an interesting order alongside aggregation) | If a later phase adds a query needing sort-based GroupBy, it isn't available yet and would need its own implementation |
2026-11-23 | QD's "free" ordered delivery applies only to `join_order=order2` with `method2=smj` | SMJ emits tuples in join-key order; order2's second (outermost) join is on `S.sid` specifically (QD's `ORDER BY`), while order1's outermost join is on `B.bid` — an SMJ there would be sorted by bid, not sid. Every other (order, method2) combination gets an explicit final `ExternalSort` instead | `RunQD` checks this one condition; `test_qd.cpp` asserts the free-delivery branch is actually exercised (`saw_free_order`), not just the fallback |
2026-11-23 | `run_query --explain` reports each join's estimated I/O and its **rank among the other three methods at that same step** (computed locally with the same M/N/B), not a rank over the full plan space | SPEC.md section 13 explicitly excludes building a cost-based optimizer *search*; a true full-plan-space rank would require evaluating every join-order x pushdown x method combination, which is exactly that search | The reported "rank" answers "was this the cheapest of the four join algorithms available at this specific step," not "was this the best of all possible QB plans" |
2026-11-23 | **Finding, not a bug:** `--explain`'s measured/estimated I/O ratio can be very low (worst seen: ~0.02) specifically for INLJ when the probed inner table is tiny (Boats: ~100 rows / ~2 pages at base scale) | The INLJ formula (`M + \|R\|*c`) charges one index-lookup cost `c` per outer tuple as if every probe were a cold read; in reality, once a 1-2 page table (plus its 1-2 page index) is touched a few times it stays fully resident in the buffer pool, so almost every later probe is a free hit. This is the same caching effect already documented for GHJ in Phase 4 (partition-thrashing finding), just in the opposite direction (the formula over- rather than under-estimates) | For experiments varying buffer size or table size (E3, E6), expect INLJ's measured/estimated ratio to improve (move toward 1) as the inner table gets too large to stay fully cached — SPEC.md's own success criterion allows deviations "explained by measured cardinalities," which this is |
2026-11-23 | `scripts/run_experiments.py` config schema: a "points" list (each a dict of overrides merged over `dataset_defaults`/`query_defaults`) replaces/extends the Phase 6 single-dataset shape, auto-detected by the presence of "points" | E1-E6 each vary a different factor (scale, selectivity, buffer size, skew, correlation, index/clustering), several needing a fresh dataset per point and others reusing one — a flat, generic override-and-merge design covers all six without one-off code per experiment | `configs/smoke.json` and `configs/qa_methods.json` (Phase 6 shape) still work unchanged via the old code path; only `configs/e1..e6.json` use "points" |

2026-11-23 | E1 sweeps scale for QA only (not QA..QD as SPEC.md's literal description allows); E2/E3/E5 fix `method1 == method2` (the same join method used for both of QB's joins) rather than sweeping all 16 method-pair combinations | Covering all four queries x all buffer sizes x all method-pairs would multiply each experiment's runtime many times over for marginal additional insight beyond what Phase 7's 64-plan sweep already demonstrated (every method pair is already known to produce correct, oracle-matching results); each experiment still varies its one named factor across all four join methods (or the two most relevant, for E4) | If the report needs same-method-pair blind spots filled in later (e.g. a mixed method1≠method2 buffer sweep), `configs/e3.json`'s `points`/`methods` can be extended without code changes |
